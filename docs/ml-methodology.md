# ML Methodology

This document describes how the prototype decides that a region is at outbreak
risk, how that decision is turned into a probabilistic forecast, and how the
models were trained and evaluated.

> **Important**: every threshold below is a *project-defined demonstration
> choice*. They are deliberately **not** presented as official epidemiological
> definitions, and the dataset is entirely synthetic.

## Prediction objective

The system predicts, one week in advance, whether a region will experience a
**high-incidence event** (`high_incidence_event = 1`), which the prototype uses
as a proxy for outbreak risk.

```
label at week t  =  high-incidence event at week t + 1
features at week t use ONLY information available up to week t
```

The forecast horizon is `PREDICT_HORIZON_WEEKS = 1`.

## Label definition (`ml/label.py`)

A region-week is a high-incidence event when **both** conditions hold:

1. **Rapid growth**: weekly case growth rate (current cases vs. the average of
   the previous 4 weeks) is greater than `25%`, **and**
2. **Elevated load**: weekly cases reach at least `1.5x` the trailing 8-week
   regional median baseline.

| Parameter | Value |
| --- | --- |
| `growth_threshold` | 0.25 (25%) |
| `growth_baseline_weeks` | 4 |
| `case_multiplier` | 1.5x |
| `baseline_window_weeks` | 8 |

The label uses only past values (the baseline is shifted by one week), and is
shifted `-horizon` to create the 1-week-ahead target. First/last weeks where the
label cannot be computed are dropped.

## Dataset

All input data is Real (`scripts/generate_data.py`) and is
**not** real epidemiological data.

| Fact | Value |
| --- | --- |
| Regions | 12 Indian cities |
| Rows | 2,256 region-weeks |
| Date range | 2023-01-02 → 2026-08-03 (188 weeks) |
| Features (after engineering) | 17 |
| Class balance (test set) | 49 positive / 372 rows |

Raw columns per observation: `date`, `region`, population, `reported_cases`,
`previous_week_cases`, `previous_month_cases`, `deaths`, `temperature`,
`rainfall`, `humidity`, `water_accumulation_index`, `population_density`.

## Feature engineering (`ml/features.py`)

All features are rolling/lag constructs computed per region so **no future
information leaks** into the model.

| Feature | Description |
| --- | --- |
| `cases_7d_avg` / `cases_14d_avg` / `cases_30d_avg` | trailing rolling case averages |
| `case_growth_rate` | current vs. previous-4-week average (clipped to [-1, 10]) |
| `rainfall_14d_avg`, `temperature_14d_avg`, `humidity_14d_avg` | 14-day environmental rolling means |
| `water_accumulation_index` | standing-water / breeding proxy |
| `population_density` | raw regional density |
| `cases_lag1` … `cases_lag4` | 1–4 week lags of reported cases |
| `season_sin`, `season_cos` | week-of-year seasonal encoding |
| `weekly_incidence_per_100k`, `cases_30d_per_100k` | per-capita burden |

Rolling windows use `min_periods=window`, so warm-up rows surface as `NaN` and
are dropped (see `WARMUP_WEEKS = 6` in `ml/config.py`).

## Train / validation split

`time_based_split` splits **chronologically per region** (last 20% of weeks held
out) — rows are never shuffled across time, so there is no temporal leakage
between train and test.

- Train: 1,452 rows
- Test: 372 rows (20%), including 49 positive events

## Models

Trained by `ml/train.py` (Random Forest is scale-invariant and uses raw
features; Logistic Regression uses a `StandardScaler` fitted on the training
set only).

| Model | Role | `class_weight` |
| --- | --- | --- |
| `model_lr.joblib` | baseline | `balanced` |
| `model_rf.joblib` | evaluated variant | `balanced`, `oob_score=True` |
| `model_rf_unweighted.joblib` | **serving model** | none (unweighted) |

Hyperparameters: 200 trees, max depth 10, min samples leaf 3, `random_state 42`.
Logistic Regression: `max_iter 5000`.

**Why an unweighted serving model?** The balanced classifiers inflate positive
class probabilities (they are tuned / re-weighted for 49/372 imbalance), which
makes every region look risky. The unweighted RF produces probabilities that
reflect the observed base rate of high-incidence events (roughly 0–93% dynamic
range), which is more useful for ranking and for the dashboard risk bands. It is
evaluated on the same held-out test weeks as everything else.

## Serving

`backend/app/services/model_loader.py` loads the artifacts once and, for each
region, computes the **latest-week** feature vector from the demo CSV, then:

- `predict_proba_main()` → `model_rf_unweighted` (probability 0–1) — the value
  shown as *Predicted Outbreak Risk* in the UI (×100)
- `predict_proba_baseline()` → `model_lr` for side-by-side comparison

Prediction date = latest observation date + 1 week.

## Explainability

`backend/app/services/explainability.py` produces per-region feature attributions
via **perturbation sensitivity analysis**: each feature is increased by one
standard deviation (of the training sample) while all others stay fixed, and the
resulting change in predicted probability is reported in percentage points.

> Demonstration-grade attribution — not a rigorous SHAP-style explanation.
> See `EXPLAINABILITY_METHODOLOGY` in `ml/config.py`.

## Limitations

- Dataset is 100% synthetic; real-world patterns (outbreak dynamics, reporting
  lag, interventions) are not represented.
- The label is a simplified proxy, not a clinical/WHO outbreak definition.
- Only one-week-ahead predictions are produced.
- Class imbalance is handled heuristically (balanced models for evaluation,
  unweighted for serving).
- Severity, priority and recommended actions are rule-based demonstration
  formulas, not public-health guidelines.
